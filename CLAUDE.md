## Admin panel
- `admin_actions` is an append-only audit log. Append-only is enforced at the DATABASE level by two triggers, both present in dev and production: a row-level `BEFORE UPDATE OR DELETE` trigger and a statement-level `BEFORE TRUNCATE` trigger, both calling `admin_actions_block_mutation()`. The TRUNCATE trigger exists because a row-level trigger does NOT fire on TRUNCATE. Never write an UPDATE or DELETE path against this table. A wrong row is corrected by appending a correcting entry, never by editing. Note that a Supabase superuser can `DISABLE TRIGGER` — the triggers stop accidents and forgetful code, not a determined hand at the console.

## Question flags & panel edits
- Flagging is IN-GAME ONLY. `POST /api/flag-question` accepts a report only while the room still exists, the reporting player is (or was) a member of it, and the question id is one the server itself recorded as served in that room this game (`room.servedQuestionIds`) — never a client-asserted id. A report arriving after the room is cleaned up (the 120s post-game `endTimer`) is rejected outright, by design: once the room is gone there's no way to verify same-room-serving. Rate limited to 10 reports per user per hour.
- `question_flags` is keyed to `questions.id` (`ON DELETE CASCADE`) — NOT to a text hash. The old `question_key` was a client-supplied SHA-256 of the question text and could not identify any of the 551 image rows sharing an identical fixed stem. The snapshot columns (`question_text`, `options`, `correct_answer`) were dropped; the admin review screen (`GET /api/admin/flags`) joins LIVE to `questions` instead, so it always shows the current row, never a stale report-time snapshot.
- The admin panel MAY edit text questions — `PUT /api/admin/questions/:id` can change the question text, the four choices, and which choice is correct, nothing else. Category, difficulty, and `image_url` are not editable: enforced server-side by a fixed-column whitelist (`QUESTION_EDIT_FIELDS`) plus explicit rejection of any unexpected body key. Image questions are review-and-deactivate only — the edit endpoint refuses outright when `image_url IS NOT NULL`.
- Every panel edit writes a row to `question_pending_master_edits`, recording the before/after in MASTER format (letters A–D, Arabic difficulty). This is an obligation, not a log: the master still holds the old text until someone mirrors the row by hand, and a master→DB sync in the meantime would silently revert the fix. The master row to correct is located by category + difficulty + `old_question` text — the master has no id column. `content-loader` REFUSES a delete+reload on any category with outstanding pending rows (see that skill).
- `questions.active` is DB-only operational state with no equivalent column in the master. Divergence sweeps must never report it as a mismatch. A delete+reload resets it to its column default (`TRUE`), so `content-loader` captures the deactivated rows before the delete and re-applies them after the insert, inside the same transaction, with a row-count check that aborts the whole load on any mismatch.
- Deactivating a question (`/questions/:id/deactivate`) never creates a `question_pending_master_edits` row — there's nothing to mirror, since `active` isn't a master column at all.
- A delete+reload cascades away that category's unresolved `question_flags` rows too (same `ON DELETE CASCADE`). Accepted: those flags point at question rows that no longer exist.
- The triage actions (`/flags/:id/dismiss`, `/flags/:id/keep`) log a HARDCODED resolution string (`'dismissed via triage'` / `'marked no issue via triage'`), not an admin-supplied reason. An `admin_actions` entry for these records that the judgement was made, not the reasoning behind it. Deliberate — triage is high-volume and low-stakes — but do not later read these entries expecting a rationale.

- `generateQuestions` returns an empty array (does not throw) on API auth failure — a broken API key shows up only as `aiFilled=0`, not as an error. Known future fix.

## Lobby & room lifecycle
- Bottom nav (profile/levels/shop/how-to-play) is hidden on the category-selection and lobby screens only — visible everywhere else. Both screens carry a fixed top-left red pill back button reusing the admin panel's `.back` style (from `admin-players.html`).
- Room state is keyed by USER ID, not `socket.id`. Each `room.players[uid]` entry holds the current `socketId` as a field. `room.host` is a user id, kept as a Number — `Object.keys(room.players)` always returns strings, so any value re-derived from a key (e.g. host reassignment) must be explicitly converted, or `===` comparisons against `socket.user.id` silently fail.
- Rejoining under the same user id (`addOrTakeoverPlayer`) takes over the existing entry rather than creating a second one: updates `socketId`, force-disconnects the superseded socket — but only after clearing ITS `roomCode` first, so its own `disconnect` handler sees "not in a room" and no-ops instead of racing to evict the entry the new socket just took. `removePlayerFromRoom` carries a second layer of the same defense: it ignores a socket that is no longer `room.players[uid].socketId`.
- `close_room` no longer exists — there is no way to deliberately terminate a populated room, by design. Host's back button on CATEGORY SELECTION (room already open) is a HANDOFF, not a close: non-destructive نعم/لا confirmation (blue styling — nothing is lost), emits the same `leave_room` a non-host uses, and the room survives with host passing to the next player. The new host sees a blocking centered modal (blue border, single «حسناً» button), not a toast. A non-host's back button reads «خروج من الغرفة» — same نعم/لا component, but its destructive/red styling.
- Exit paths are deliberately NOT all the same anymore: `leave_room` and `kickUser` (admin ban) always call `removePlayerFromRoom` and remove the player fully, regardless of room status. A `disconnect` does the same ONLY while `status==='waiting'`; mid-game it calls `markPlayerDisconnected` instead, which marks the player `connected:false` and leaves their score and host status untouched — a mid-game drop must not evict the player, since a rejoin path exists to bring them back (see below).
- Disconnected players never count toward the "everyone answered" check (`maybeAdvanceQuestion`), on EITHER side of the comparison. A disconnected player's `room.answered[uid]` entry is never purged (only wiped wholesale when the next question starts), so excluding them from just the denominator would let their stale `answered:true` inflate the numerator and cut the round short for whoever's left. Both `total` and `answeredCount` are computed over the same connected-and-not-excluded set.
- `room.advancing` is a one-shot per-question guard: whichever of {the last required answer, a disconnect that leaves nobody left to answer, the 15s timeout} gets there first sets it and does the advancing — the others become no-ops. Without it, e.g. an answer immediately followed by a disconnect would double-increment `qIndex` and leak a timer (`askQuestion` overwrites `room.timer` without clearing the previous one first). Cleared only when the next `askQuestion` call actually starts a new question.
- Rejoin: `join_room` lets a user id ALREADY in `room.players` back into a game in progress; anyone else still gets «اللعبة بدأت» — no new player may enter a started game. A returning player is excluded from whatever question is currently live (`player.excludedThisQuestion`) and joins in properly starting at the NEXT question — the flag is cleared for every player, not just the one who rejoined, the moment `askQuestion` sets up a new question. The client never re-renders the question they rejoined mid-way through; it shows a generic waiting placeholder («ستنضم في السؤال التالي») until the real next `question` broadcast arrives. An automatic client-side prompt (room code stored in `localStorage`, keyed per user id so different accounts on one device don't clobber each other's stored code) offers this rejoin on load via a side-effect-free `check_rejoin` → `rejoin_available` round trip that leaks no room details either way, regardless of the answer.
- Timers: `ROOM_IDLE_MS` = 30 min for a room still in `waiting` (see below). `ROOM_ABANDON_MS` = 2 min, starts once EVERY player has disconnected mid-game (`markPlayerDisconnected`'s all-disconnected branch) — `room.timer` is cleared (nobody's there to answer), but `room.players`, scores, and host status are left intact. If the window expires, the room is deleted and every timer on it cleared — players are NOT refunded for this (see Currency charge boundary). If someone rejoins first, `resumeAbandonedRoom` cancels the abandonment timer and silently retires whatever question was frozen — NOT a reveal, since nobody was present to see the countdown end and broadcasting the answer would just hand it out for free: it emits `question_reset` (no `correct_answer` field) instead of `time_up`/`reveal_answer`, then keeps the same 2.5s gap before the next question, during which `room.advancing` stays true so the returning player is correctly treated as a between-questions rejoin, not excluded from anything. The existing 120s post-game timer (`room.endTimer`, set in `endGame`) is separate and unchanged. `askQuestion` also won't start a new ticking timer if nobody's connected when it runs — the advance-scheduling `setTimeout` calls aren't connectivity-aware and can't be cancelled (no stored id), so without this guard a room could cascade through unattended questions even across the 2.5s/abandonment gap.
- Any `await` followed by using a captured room reference must re-check `rooms[code] === room` before touching it — `start_game`'s `buildRound` calls and `endGame`'s DB writes both do this. Room codes are 4 digits with no collision avoidance, so a room can be deleted (or even replaced by an unrelated new room reusing the same code) while an await is in flight.
- `getPlayers` emits ONLY: `id`, `display_name`, `level`, `total_score`, `sessionScore`, `isHost`, `connected`, `answered`. It must never spread the full player object into a broadcast — `room.players` also holds `email`, `phone`, `dob`, `gender`, and `socketId`, none of which belongs in a payload every player in the room receives.
- Gendered Arabic strings (e.g. the presence-banner leave/rejoin text) are conjugated SERVER-SIDE — only the rendered word is broadcast (`player_presence`'s `verb` field), never the raw `gender` field. Same boundary as the `getPlayers` rule above: any new socket payload that touches gender must compute the final string and send that, not the field itself.
- One account, one room: `create_room` and `join_room` call `leaveOtherRooms` first, which evicts the user id from any OTHER room it's currently a member of (any status — waiting, mid-game, doesn't matter), reusing `removePlayerFromRoom`'s cleanup and notifying+disconnecting the stale socket if it's still live. Rejoining the SAME room the user is already in is excluded from this check — that stays the takeover path (`addOrTakeoverPlayer`), untouched.
- `update_room_categories` is still host-guarded on both the client (no UI path exposed to non-hosts) and the server (`room.host !== socket.user.id`) — a tampered client can't bypass either.
- Idle-lobby timeout (`ROOM_IDLE_MS`, unrelated to the abandonment window above) is reset on `create_room`, `join_room`, `update_room_categories`, and centrally inside `removePlayerFromRoom`. Cleared when `start_game` leaves `waiting`; resumed if `start_game` fails back to `waiting`, and restarted on `play_again`.
- No ready system: the host's start button begins the game immediately regardless of other players' state. No per-player ready flag exists anywhere in the code.
- Centered popups (dark box, colored border, same shape as the max-selection one) are reserved for blocking/important events only — category limit reached (auto-dismissing), or the leave/handoff/rejoin confirmations and new-host notice (blocking, require a button press, blue "non-destructive" variant alongside the original red). Routine successes (e.g. saving edited categories) get no popup or toast; a live-updating view is the feedback.

## Currency charge boundary (design law, not yet built)
- The pulp is deducted server-side in the SAME transaction that dispatches question 1 of round 1 (the single `io.to(code).emit('question', ...)` in `askQuestion()`, server.js ~932). Never earlier. Leaving before that moment is free — this is a CONSEQUENCE of where the charge fires, not a feature to build. Nothing to enforce, no refund path, no race.
- Free-leave is a SILENT GRACE: no leave button, no UI mention of it during the countdown. Advertising it invites abandonment. The only exit during the countdown is therefore a disconnect (tab close, app background, browser back) — which is what makes the grace self-enforcing. VERIFY before building: confirm the s-phase screen carries no back/leave control inherited from the category-UI overhaul. If it does, hide it during phase 0 rather than leaving a one-tap free exit on screen.
- Minimum players is 1. If players bail during the countdown the game continues normally for whoever remains; there is no abort path. If ALL players leave, the room is deleted and `askQuestion()` no-ops via its existing `if (!room || room.status !== 'playing') return;` guard, so the charge never fires. This case needs no new code.
- TIMING GAP — reviewed and ACCEPTED, do not "fix" this: the server dispatches question 1 at `phase_start` + 3000ms (`setTimeout` in `startPhase`), but the client does not display it until `introEndsAt` = phase_start arrival + 3850ms (`runIntroCountdown`, index.html ~1332). The charge therefore fires ~850ms + one leg of latency BEFORE the player sees question 1. This gap is stable, not drifting — latency delays the countdown start and the question arrival equally, so it cancels. Decision: leave both timers as they are. With silent grace and no leave button, nobody can deliberately exploit a sub-second window they cannot see. The real cost is the rare unlucky disconnect inside that window — a player charged for a game where no question ever appeared — and the mitigation is the admin manual-refund tooling on list B, NOT a timing change. REVISIT this decision if either of these changes: (a) the admin refund tooling is cut from scope, or (b) the client intro countdown is lengthened beyond 3850ms, which widens the gap proportionally.
- "Auto-refund for crashed games" means the GAME crashed (server-side failure / room collapsed) — NOT that a player dropped. A player drop and a rage-quit are indistinguishable at the socket level, so refunding on player drop would be a refund button in disguise.
- MONEY RULE: when the 2-minute abandonment window (`ROOM_ABANDON_MS`, see Lobby & room lifecycle) expires with nobody having returned, the room is deleted and players are NOT refunded — the game was delivered and they had two minutes to come back.
